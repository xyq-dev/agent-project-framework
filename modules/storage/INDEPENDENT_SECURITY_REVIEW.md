## OSS-001 findings and required profile

The official PutObject contract confirms the two decisive constraints: a versioning-enabled bucket returns a unique version ID for each new object, while `x-oss-forbid-overwrite` is ineffective when versioning is enabled or suspended; it also warns that an undersized `Content-Length` can publish a truncated object. The official GetObject contract returns the current version by default and may return a full `200` response for an invalid Range. ListObjectsV2 does not return custom user metadata. These facts rule out ETag-as-revision, HEAD+PUT creation/CAS, direct upload from an incompletely validated source, blind Range acceptance, and list entries constructed without enrichment.

The conservative profile is safe to implement under the current public Storage API subject to every requirement below.

### Signed download design boundary

The initial OSS profile keeps both signed capabilities disabled because the current `StorageAdapter` has no signer method and `createStorage` deliberately rejects those descriptors. This is a safe limitation, not an incomplete success path. `signed-upload-url` must remain disabled because this profile cannot enforce the default absence condition.

A later `signed-download-url` increment is design-feasible only after a minimal reviewed port change: add an optional validated adapter signer method, let Core dispatch it only when that capability is present, and keep upload/move/multipart in the hard-disabled set. It must use the pinned official V4 signer; re-check the SDK debug boundary before credentials; bind GET, fixed HTTPS origin/bucket/physical key/region and every required header; accept no caller SDK options; and parse the result back to prove those bindings. Effective TTL is no more than the requested/default TTL, 900 seconds, the SDK/provider limit, and credential expiration minus a fixed clock-skew margin. Insufficient lifetime rejects before signing. Return all required headers and an `expiresAt` no later than the effective limit. The URL is a bearer secret: never log it, promise revocation/single use, or claim a download occurred. This later port and its security tests require separate implementation review; OSS-001 does not enable it.

### I-001 internal cancellation bridge — accepted with mandatory lifecycle conditions

Adding `cancel(): void` to the adapter-facing internal `OperationContext`, implemented by `Context` as an idempotent `#abort('aborted')`, is an acceptable way for Local `close()` to cancel Core deadlines and a `guardedInput`/`managedRead` wait. It must not be added to the consumer-facing `Storage` interface, call `finish()` on the adapter's behalf, reset a dispatched outcome, or itself release an adapter lease. A close-triggered cancellation before dispatch remains `not-applied`; cancellation after `markDispatched()` remains `unknown`. Core must demonstrably clear the operation timer and external abort relay when the rejected operation or returned managed body finishes.

Local must register every accepted context before starting work, atomically reject new work after entering `closing`, and call `cancel()` on all registered contexts and returned snapshots. The adapter's lease is a separate lifetime: rejection from `context.wait()`, iterator cancellation, or completion of the public Promise must not release it while a raw `open/read/write/fsync/rename/unlink/close` Promise can still settle. The lease retains the key mutex, staging reservation/path ownership, FD and writer-lock dependency until the actual I/O and required handle close settle. `close()` waits those leases. If its own close deadline expires, it returns timeout, retains the writer lock and remains closed; later lease settlement must not auto-unlink the lock. A later explicit `close()` retry may drain again and unlink only after the lease count is zero and the original lock inode/token is reverified. This is an allowed completion of the same failed-closed shutdown, not a stale-lock recovery path.

Implementation evidence must include cancellation while blocked in input `next()`, open/read/write, non-cancellable rename/unlink, and a returned but never-consumed snapshot; each case must show the Core wait/timer ends, the raw operation remains leased until actual settlement, the FD/temp ownership is released exactly once, and the lock is not removed early.

### I-002 OSS user-metadata envelope — accepted with exact reserved-header conditions

The first OSS profile may store the complete APF `UserMetadata` map only in reserved `x-oss-meta-apf-user` as unpadded base64url of UTF-8 canonical JSON. It must not project individual user keys into `x-oss-meta-*` headers. Format, namespace binding and logical-key digest use separate fixed reserved headers; the namespace and key markers are unpadded base64url SHA-256 digests over their exact validated UTF-8 values with an unambiguous domain/version definition. Thus valid user keys such as `apf-user` or `apf-format` remain ordinary keys inside the JSON map and cannot collide with transport metadata.

Encoding sorts keys deterministically and uses one specified JSON serialization. Decoding must bound the encoded header before allocation, accept only canonical unpadded base64url, use fatal UTF-8, reject duplicate/unknown JSON structure through canonical round-trip validation, and then apply the existing exact `UserMetadata` validation and 2 KiB decoded-map limit. Header processing is case-insensitive and must reject missing, duplicate or aliased reserved headers, any unknown `x-oss-meta-apf-*` field, malformed hashes/JSON, and format/namespace/key mismatches as `integrity-error` before exposing `ObjectInfo` or body. The same checks apply to current GET/HEAD, version-specific PUT confirmation, list enrichment and copy. Raw or encoded user metadata must never enter diagnostics.

One O-003 length omission must be resolved in code: `apf-storage/v1/<base64url(UTF8(namespace))>/objects/<logical-key>` can exceed the provider object-key limit when both public inputs approach their allowed 512 UTF-8 bytes. Use a fixed-length namespace digest in the physical prefix, while retaining the independent namespace marker above, unless tests and a provider-limit calculation prove every API-valid namespace/key pair fits. Silently narrowing the public key/namespace contract is not approved.

Required offline cases include user keys matching every reserved suffix, empty and 2 KiB-boundary maps, quote/backslash-heavy values, reordered input, non-canonical/padded base64url, invalid UTF-8, duplicate JSON keys, missing/extra/case-aliased reserved headers, namespace/key hash mismatch, maximum-length namespace plus key, and exact round-trip through put/get/head/list/copy. These are fake-transport/implementation requirements only. No test bucket or credentials were supplied, so real OSS verification remains **NOT_RUN**.
